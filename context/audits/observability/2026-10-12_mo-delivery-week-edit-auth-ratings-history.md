# Observability audit: MO delivery, week edit, auth, ratings/history (2026-10-12)

## 1. TL;DR

- **Sentry only sees exceptions that are thrown.** The app catches every failure it expects and turns it into a friendly page, a JSON error code, a redirect or a 200. It then writes one `console.error` message string. Sentry gets nothing, which the probes P4 and P6 proved. There is exactly one `captureException` in `src/`, at `src/middleware.ts:38`. This is the documented policy (`docs/deployment.md:96`), but in practice it means none of the realistic outages in the four flows reaches Sentry: a database outage, an Auth outage, a migration that breaks a grant, or an email rate limit.
- **An Auth outage looks like everyone signing out.** `src/middleware.ts:21-24` never reads the `error` from `getUser()`. A GoTrue outage, or a missing `SUPABASE_*` secret, sends every user to `/auth/signin` and leaves no log line at all.
- **System faults are relabelled as user errors or as success.** Examples: `verifyOtp` failing for any reason shows "link expired"; a failed reset email still shows "we've sent a link"; a failed invitation answers MO with 200 `account_created: true`, and the user is never invited.
- **Errors after the page starts streaming escape every boundary.** P10 proved it: a child `.astro` component that throws produces a **truncated page with status 200**, no Sentry event and no app log. `docs/deployment.md:92` ("errors thrown in a page … reported") overstates what is covered.
- **Empty results count as normal.** An RLS, filter or grant regression gives zero rows. The UI then shows "No upcoming plan yet", "Plan not found" or unrated meals, as 200 or 404, with no log.
- **Errors lose their detail along the way.** Services rebuild Supabase errors as `new Error(\`${code} ${message}\`)`without a`cause`. Logs carry the message only, with no stack, PostgREST `details`/`hint`, route or entity id. Browser islands collapse every fetch failure to `status: 0`.

## 4. Systemic root causes

1. **"Handled" means "never reported", and no shared reporting helper exists.**
   - **Mechanism:** every `catch` and `{ error }` branch ends in `console.error(<message string>)` plus a friendly response. Examples: `src/lib/plan-save.ts:15-18,43-48`, `src/pages/api/ratings.ts:34-40`, `src/pages/api/mo/deliveries.ts:51-54,154-161`, `src/pages/dashboard.astro:39-43,53-63`, `src/pages/history/index.astro:20-23`, `src/pages/history/[id].astro:21-28`.
   - **Why it exists:** the Sentry change (S-07) deliberately limited reporting to unhandled errors (`docs/deployment.md:96`). The free plan has 5,000 events a month, and the policy avoided noise.
   - **Effect:** Sentry never sees a database, PostgREST or GoTrue outage, and nothing alerts. The dashboard and history fallbacks answer 200, so even status-code dashboards miss them.
   - **Explains:** D2, W3, W6, R2, X3, A6, D10 and the "console only" part of most other findings.

2. **The auth boundary reads Supabase results only partway.**
   - **Mechanism:**
     - `src/middleware.ts:21-24` destructures `data.user` and ignores `error`.
     - `src/pages/api/auth/set-password.ts:69-74` does the same on the retry path.
     - `src/lib/supabase.ts:7-9,32-34,46-48` returns `null` with no log when a secret is missing. The secrets are all `optional: true` (`astro.config.mjs:48-51`).
   - **Why it exists:** a `null` user is the normal "signed out" case, and optional secrets keep local dev and CI booting.
   - **Effect:** an Auth outage or a missing secret produces the same 302 to sign-in as an expired session, with no log.
   - **Explains:** X1, A3, X4, D3, and the 401 or redirect side of W4 and R4.

3. **Each route maps errors to a code chosen by the user-facing message, not by what failed.**
   - **Mechanism:**
     - `set-password.ts:61-64`: any `verifyOtp` error gives `invalid_link`.
     - `forgot-password.ts:34-38`: any error gives `?sent=1`.
     - `signin.ts:30-33` with `src/lib/signin-errors.ts`: anything unknown gives `sign_in_failed`, and wrong passwords are logged at `console.error`.
     - `deliveries.ts:120-135`: a failed invitation gives 200 `account_created: true`.
     - `deliveries.ts:154-156`: an invalid service key gives `storage_failed`, which MO treats as retryable.
     - `plan-save.ts:44-46` and `api/ratings.ts:36-38`: 404 and 409 are never logged.
   - **Why it exists:** sensible user-facing choices (don't reveal which accounts exist, keep the week stored, give friendly copy) with no separate signal for the operator.
   - **Effect:** a responder can't tell a system outage from user mistakes, and some outages look like success.
   - **Explains:** A1, A2, A4, D1, D4, D6, W4, R4.

4. **The middleware `try` around `next()` ends before the streamed body is rendered.**
   - **Mechanism:** `src/middleware.ts:12-39` wraps `next()`. Astro streams by default (`astro/dist/core/app/base.js:73`) and reports body errors only through `controller.error` (`render.js:62-72`). Sentry's stream wrapper doesn't capture (`wrapRequestHandlerWithInit.js:91-113`).
   - **Why it exists:** the S-07 fix correctly closed the "Astro swallows page errors" gap for frontmatter and endpoints. The streaming phase was not covered.
   - **Effect:** proven by P10. A render bug in `WeekPlan.astro`, `MealSlot.astro`, `Layout.astro` or island SSR on the dashboard or history gives users a truncated 200 page, with no event and no app log.
   - **Explains:** X2.

5. **Zero rows and fallbacks are treated as legitimate data.**
   - **Mechanism:**
     - `maybeSingle()` returning `null` means "no plan" (`src/lib/services/plans.ts:25-40,53-69`).
     - Security-invoker RPCs return empty sets (`get_plan_ratings`, `get_plan_recency`), and `result.data ?? []` passes them on (`src/lib/services/ratings.ts:81`).
     - The `meal_ratings` embed comes back `null` (`src/components/plan/MealSlot.astro:27`).
     - A slot with no chosen option falls back with `?? first` (`src/lib/plans.ts:98`).
   - **Why it exists:** RLS is meant to filter silently. An empty result is the normal answer for a new user.
   - **Effect:** a policy, grant or date-filter regression shows up only as empty or "not found" UI.
   - **Explains:** W2, R1, R3, R5. The main guard here is tests (S-03 data isolation), not runtime monitoring. A few cheap invariant logs help.

6. **Error identity is flattened to a string at the first boundary.**
   - **Mechanism:**
     - Errors are rebuilt as `new Error(\`… ${code} ${message}\`)`with no`cause`: `src/lib/services/plans.ts:38,67,94,123,147,193`, `src/lib/services/ratings.ts:47,78`, `src/lib/keepalive.ts:18`.
     - Logs are message-only, and the same `"weekly_plans query"` label is used for 4 queries.
     - Client fetch wrappers return `{ ok: false, status: 0 }` for every failure (`src/components/hooks/usePlanChoices.ts:35-47`, `src/components/hooks/useMealRating.ts:18-28`).
     - Server events carry no route or transaction (P1).
   - **Effect:** even the failures that are logged are slow to diagnose, and browser save failures leave no trace anywhere.
   - **Explains:** X5, D5, W5, W7, R6, R7, X7, X8.

## 6. Recommended fix order

1. **Read auth errors at the boundary** (X1, A3, X4; also closes the "signed out" side of W4 and R4). This is a few lines in `src/middleware.ts` and `set-password.ts`, plus a once-per-isolate warning in `src/lib/supabase.ts`. It removes the largest invisible failure, a site-wide sign-out with no log. Constraints: never capture the user or email, and keep `AuthSessionMissingError` silent, since it is the normal anonymous case and would be pure noise.
2. **Add a shared `reportHandledError` helper and use it on every `failed` branch and 200 fallback** (X3, D2, W3, W6, R2, A6, D10, plus X5 by passing `{ cause }` in the services). This is one new helper in `src/lib/` and about 12 call sites. Constraints:
   - Fingerprint by `step` + `pg_code` so a database outage is one issue, not thousands. The free plan has 5,000 events a month, and the Dedupe integration already drops identical consecutive events.
   - Messages go through `scrubEvent` (emails masked), but PostgREST `details` can echo row values. Send `code` and `hint`, and keep `details` in tags only after checking they contain no user data.
   - The change rewrites the policy at `docs/deployment.md:96`, so it must update that doc in the same PR (CLAUDE.md docs rule).
3. **Separate system faults from user errors in auth and delivery** (A1, A2, A4, D1, D3, D4, D6). Route by `status >= 500 || status === 0 || code unknown` into the helper from step 2. Keep the user-facing copy (no account enumeration) and add `invitation_sent` to the MO response. That is a contract change: update `docs/mo-delivery-contract.md` and `moDeliverySchema` notes together.
4. **Capture streamed render errors** (X2). In the middleware, return a `Response` whose body reads the original stream and calls `captureException` when a read fails. Alternatively, disable streaming if `@astrojs/cloudflare` exposes it; that trades time-to-first-byte for correct status codes. Prove it with probe P10 before and after, then fix `docs/deployment.md:92`.
5. **Make browser saves report and stop reverting committed saves** (W5, R6, X8). Capture in the `postSave` and `postRating` catch blocks and for ≥500 responses; add an island error boundary.
6. **Log the "expected" outcomes that faults can produce** (W4, R4, R3, D7, W10, A5, A8, W9): 404, 409, 400 and 401 lines with a reason and a stable prefix, so they can be counted. Add invariant logs for W2, R1 and R5. Guard the RLS regressions behind them with the S-03 data-isolation tests rather than runtime checks.
7. **Then the low-severity polish** (X6, X7, D9, A9, A10, R7, R8, W7, W8, D5, D8).
